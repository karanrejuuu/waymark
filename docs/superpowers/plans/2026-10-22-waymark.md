# Waymark Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build Waymark — a hosted, installable PWA that tells an FMCG distributor's delivery person which shops to visit today, lets them mark deliveries done in two taps, and self-corrects intervals from cheap field signals.

**Architecture:** Next.js 14 App Router (TypeScript) deployed on Vercel, Supabase (Postgres + RLS + Auth) as the server, Dexie.js (IndexedDB) as the offline-first local store with a Background Sync service worker draining a write queue to Supabase on reconnect. All reads come from Dexie; the UI never awaits a network call for rendering.

**Tech Stack:** Next.js 14, TypeScript, Tailwind CSS, Supabase (Auth + Postgres), Dexie.js, Zustand, Leaflet, Lucide icons, Vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-10-22-dukaan-rounds-design.md` — the plan argues from the spec; executors read both.

- Font: Inter (Google Fonts), weights 400/500/600. Scale: 14px body, 13px meta, 20px page title, 16px section header.
- Icons: **Lucide** only — 16–18px, `--text-secondary` fill, no emoji as icons.
- Spacing: 4/8/12/16/24/32/48px — no arbitrary values.
- Border-radius: 6px buttons/inputs, 8px containers, never pill-shaped.
- Animation: 120–150ms ease-out on hover/opacity only. Checkbox tick on Today screen: ~150ms, nothing else moves.
- No gradients, no box-shadows on cards, no colored pill badges, no mascot illustrations.
- Touch targets: ≥ 44px height on all interactive elements.
- `touch-action: manipulation` on all buttons to eliminate 300ms tap delay.
- Scheduling formula: `next_due_date = delivered_at::date + interval_days - remind_offset_days`.
- Interval self-correction: `low → max(1, interval-1)`, `plenty → min(60, interval+1)`, `fine → no change`. Fires per-product at confirm time.
- `is_urgent = true` → `next_due_date = today`; resets to `false` on delivery.
- `next_due_date` defaults to `today` on `shop_products` insert.
- `qty` pre-filled from `default_qty`; never required to type.
- Owner role: CRUD on shops, products, regions, intervals. Delivery role: mark delivered, flag urgent, stock feedback.
- Timezone: IST (UTC+5:30) for server cron; browser local date for Dexie reads.
- Expense estimator: haversine distance with `≈` prefix.
- All writes go to Dexie first, then sync queue. Delivery records are immutable (append-only).
- No emojis as UI icons (stock feedback 🔴🟡🟢 taps are the sole exception per spec).
- RLS: every table has `owner_id` or is scoped to the authenticated user.

## Review Focus

The five input classes most likely to bite a real user that no single task's tests fully exercise:

1. **Offline → online sync with duplicate prevention** — a delivery recorded offline then synced must not create a second `deliveries` row on re-sync. The sync queue must be idempotent (upsert by a stable client-generated UUID).
2. **Timezone boundary at midnight IST** — a shop due on 2026-10-22 must appear in Today as of 00:00 IST (not 18:30 UTC the night before). Dexie reads use `new Date()` local date; tests must assert against IST midnight boundaries.
3. **Multi-product confirm — partial data** — if the expand shows 3 products and the user changes one qty, the other two must still use `default_qty`, not zero or null. Confirm writes 3 rows.
4. **Interval floor/ceiling** — `low` on a shop already at `interval_days = 1` must not go to 0. `plenty` on a shop at 60 must not exceed 60. Unit tests must assert both boundaries explicitly.
5. **Urgent flag race** — if delivery person marks urgent offline and owner clears it concurrently, the sync merge must not silently discard either. Resolution: server wins on `is_urgent` updates (last-write-wins by `updated_at`); the sync queue payload includes `updated_at`.

Each of these gets its explicit test in the owning task below.
